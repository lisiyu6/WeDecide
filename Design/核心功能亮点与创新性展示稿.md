## 一、项目核心定位：把群体分歧转化为可执行的协商流程

多人决策的困难，往往不在于缺少选项，而在于每个人表达需求的方式不同、个人底线与偏好混在一起、讨论过程不断变化，以及最后的赞成是否针对同一份方案。

WeDecide 围绕这条真实链路组织产品：成员独立表达，AI 整理为待确认需求，工具校核共同方案，成员协商取舍，最后针对冻结版本正式表决，并在参与意愿变化后重新检查执行条件。

**这套系统的技术价值，可以概括为三个层次：**

1. **理解层：把人的话转化为能参与计算的条件。** 动态卡片依据真实候选差异和算法缺口提问，用户确认后才形成正式偏好。
2. **推演层：让 AI 解释有计算依据的结果。** 硬约束、费用、公平性评分由确定性引擎计算，Agent 读取工具结果后继续协商。
3. **治理层：让每次修改、每轮投票都有明确边界。** 个人授权、版本校验、投票快照、过期结果拦截共同维持决策的一致性。

> **开场金句：** WeDecide 把“大家商量一下”变成一条有依据、有权限、有版本的决策流程：每个人的底线先被认真听见，每个方案先接受真实校核，每个共同决定再由成员亲自确认。

### 一张表讲清技术分工

| 层次 | 实际职责 | 对应代码 |
|---|---|---|
| 交互层 | 卡片访谈、按需输入、角色相关下一步、方案与投票展示 | `web/interview-input.js`、`web/flow.js`、`web/app.js` |
| Agent 编排层 | 读取房间状态、生成候选草稿、调用校核与模拟、解释取舍 | `agent.py`、`decision_tools.py` |
| 确定性计算层 | 必要条件校验、费用拆解、个人与群体评分、有界行程搜索 | `engine.py` |
| 业务规则层 | 本人确认、房主核对、条件变更、版本失效、正式投票 | `domain.py` |
| 运行支撑层 | 模型协议适配、结构修复、异步队列、SQLite 事务、SSE 通知 | `ai.py`、`store.py`、`realtime.py`、`app.py` |

这一分工可表述为 **“大模型语义能力与确定性决策引擎的混合架构”**。这里的创新重点是机制如何协同工作，不是宣称发明了新的基础模型或数学算法。

## 二、第一梯队：六个最值得讲透的代码级亮点

### 01. 算法契约驱动的动态访谈：每一个问题都要对决策有用

**用户价值**

成员不必填写一张大而全的问卷。AI 根据已有表达、候选差异与实际冲突，追问能影响方案可行性或排序的信息。

**代码已经做了什么**

- `interview_algorithm_context()` 向模型提供真实的 `supported_fields`、已有条件、候选属性差异、事实缺项，以及当前方案对本人的实际影响。
- 每张继续追问的卡片必须包含 `targets` 和 `purpose`：准备补充哪个算法字段，为什么要问。`read_interview()` 会拒绝缺少有效目标或用途的卡片，并进入有限修复流程。
- 只有通用备选时，访谈契约会移除活动时间相关字段，避免机械地追问无关行程问题。
- 系统区分“成员需要表达的偏好”与“房主需要核对的候选事实”。缺少价格、来源等事实，不能靠追问成员的喜好补出来。
- 每轮最多四张问题卡；重复问题、主动结束和问题上限都会触发收拢。结束一个未回答的可选追问，不应凭空增加用户必须解决的条件。

**专业表达**

算法契约驱动交互（Algorithm-grounded Interaction）、决策相关性约束、结构化偏好建模。

**展示话术**

> 我们给 AI 的每一次追问都设了一道门槛：这个问题要补充哪个计算字段，会影响哪一种取舍？问题与真实算法脱节，就不能直接进入用户界面。这样，访谈会围绕当前决策的信息缺口展开。

**代码依据：** [访谈算法上下文][C01]、[访谈策略与字段校验][C02]。已有用例检查“没有计算目标的问题被拒绝”和“四问后结束整理”。[T02]

**表达边界：** 这是依托规则和候选证据的动态提问，尚不是经过实验验证的信息增益最优化或主动学习算法。

### 02. 受控 Agent 工具闭环：先真实计算，再解释取舍

**用户价值**

“AI 已经分析过了”有对应的执行结果，而不是只有一段听起来合理的文字。

**代码已经做了什么**

- `agent.run()` 支持 `analyze`、`simulate`、`respond` 三种动作，应用根据结构化输出分派实际工具。
- `analyze` 真正调用 `engine.generate()`，再把校核结果交回模型，让下一步解释建立在当前输入版本上。
- 全员确认、候选就绪但尚无当前计算结果时，即使模型直接选择回答，程序也会先执行校核。
- `tool_results` 保存工具名、输入版本、分析版本及聚合结果等执行记录。
- 单次 Agent 运行设三次逻辑模型调用预算，结构修复也消耗预算；同一轮中 `analyze` 与 `simulate` 各最多执行一次，避免反复绕圈。

**专业表达**

工具增强 Agent（Tool-augmented Agent）、有界编排（Bounded Orchestration）、基于执行证据的解释（Execution-grounded Explanation）。

**展示话术**

> WeDecide 的 Agent 能把问题交给真实工具计算，再读取结果继续协商。它说“这个方案满足条件”，背后应该有本轮校核；它说“换一种权衡可能更好”，背后应该有一次明确标注的模拟。

**代码依据：** [Agent 执行循环][C03]。已有用例覆盖“模型跳过分析仍触发计算”和“分析—模拟—解释的三步调用”。[T01]

**表达边界：** 当前是应用层 JSON 工具分派，不依赖所有供应商支持原生 Function Calling。三次是逻辑调用预算；协议兼容回退可能增加实际 HTTP 请求次数。

### 03. 计算与解释分离：AI 暂时失败，也能保住已完成的决策进度

**用户价值**

成员已经确认的需求、已经计算的方案，不应因为一次模型超时或格式错误全部重来。

**代码已经做了什么**

- 关键业务操作完成后，`room_action()` 检查是否需要分析；数据就绪时直接进行确定性计算，无需等待模型写完解释。
- `preserve_progress()` 在模型说明失败、结构修复失败或预算用尽时，保留已有工具结果和仍有效的草稿；满足计算前提时也可补做实际校核。
- 访谈结构失败会保留上次有效草稿并给出明确提示，不将新回答虚构成已提取成功的条件。
- 场景与 Agent 候选逐项校验，一个坏条目不会必然拖垮其他有效候选。
- 上游空回答、输出截断和无效结构有独立处理路径，不直接包装为成功。

**专业表达**

故障隔离、渐进降级（Graceful Degradation）、部分结果保全、计算与解释解耦。

**展示话术**

> 我们把计算结果和 AI 的文字解释分开保存。模型暂时不能解释，不等于已经完成的计算失效。系统会明确说明哪一步没有完成，同时把用户已经走过的路保留下来。

**代码依据：** [关键操作后的即时校核][C04]、[Agent 进度保全][C05]、[结构修复与候选逐项校验][C06]。对应回归用例覆盖上游故障后保留真实结果。[T01][T02]

**表达边界：** 这是特定失败路径下的保全机制，不是零故障承诺；断电、数据库故障及跨进程任务恢复不在这项能力的保证范围内。

### 04. 硬约束优先 + 公平性感知评分 + 非支配方案比较

**用户价值**

方案先尊重每个人确认的底线，再讨论整体满意度和弱势体验，避免仅凭一个平均分掩盖个人冲突。

**代码已经做了什么**

- `evaluate()` 与 `evaluate_decision()` 分别处理活动行程和通用备选，检查预算、时间、地点、排除类别和动态属性条件。
- 必要预算按费用上界检查；固定费用按参与人数分摊，活动费用还包含配置的转场费用。
- 明确违反必要条件时标记 `INFEASIBLE`；缺少判断所需事实时标记 `UNKNOWN`。
- 群体比较采用平均预测满意度与最低预测满意度的加权组合，默认公平性权重为 `0.3`。
- `comparison_digest()` 在当前可行候选、共同已知且至少两个有效维度上计算支配关系，给出已知维度上的非支配集合，并分别指出费用、群体分和最低预测满意度视角下的方案。

```text
群体比较分 = (1 − λ) × 平均预测满意度 + λ × 最低预测满意度
默认 λ = 0.3
```

**专业表达**

硬约束优先的多目标评价、公平性感知排序、已知维度上的 Pareto 式非支配比较。

**展示话术**

> 我们把“能不能接受”和“更喜欢哪一个”分开处理。个人底线先决定方案是否可行，再比较整体收益与最低预测满意度。面对多个各有优势的方案，系统会把取舍展示出来，让成员选择。

**代码依据：** [确定性评价引擎][C07]、[非支配比较摘要][C08]、[规则默认值][C09]。

**表达边界：** 分数是规则计算的偏好匹配指标，不是经过校准的真实心理满意度。未知分数不补零，聚合只使用已有有效分数，并标记覆盖率和部分评价；非支配集合也不构成全局最优证明。

### 05. 只读 What-if 推演：用同一套引擎验证“如果换一种安排”

**用户价值**

成员可以探索更重视最低满意度、或改变活动安排后的影响，而不会把一次试想误写成正式规则。

**代码已经做了什么**

- `simulate()` 对房间做 `deepcopy()`，在隔离副本中修改公平性权重或替代行程。
- 模拟复用正式 `engine.generate()`，返回实际计算的候选、费用、比较分和警告。
- 替代行程必须引用当前房间已有活动资源；模拟前也检查成员确认及决策阶段。
- 结果带 `hypothetical=true` 和输入版本，只返回聚合证据，不写回正式偏好、规则或投票方案。

**专业表达**

只读情景模拟、反事实式方案比较、计算逻辑复用、模拟与正式状态隔离。

**展示话术**

> 协商里最常见的一句话是“要不换一种试试”。WeDecide 可以把这句话落到同一套计算引擎上，让大家看到变化带来的结果，同时保留正式决定的边界。

**代码依据：** [只读模拟工具][C10]。测试通过比较运行前后的完整房间对象，检查模拟没有改动正式状态。[T01]

**表达边界：** 当前参数主要是公平性权重与既有活动资源的替代行程，不支持任意个人条件模拟，也不等同于因果推断或数字孪生。

### 06. 多层版本控制：让异步 AI 与多人操作对齐同一份事实

**用户价值**

一个人更新需求、另一个人确认方案、AI 还在生成解释时，系统不会仅凭“谁最后返回”决定哪份内容有效。

**代码已经做了什么**

| 版本或标识 | 控制的问题 |
|---|---|
| `revision` | 普通房间操作是否基于最新快照 |
| `preference_version` | 本人的需求是否已经在其他页面修改 |
| `input_version` | 计算是否仍对应当前成员、候选和条件 |
| `context_version` | Agent 是否读到了最新共同背景 |
| `knowledge_version` | 房主知识是否发生并发覆盖 |
| 投票 `session_id` | 这张票是否属于当前轮次 |

- `mutate()` 对个人偏好、投票、反馈等采用独立检查路径，避免其他人的正常操作导致无关的全局版本冲突。
- 异步 Agent 回调检查输入版本、上下文版本、轮次及当前阶段；过期结果标记 `stale`，不能直接安装成正式分析。
- 当前已有有效分析时，迟到的计算不会再次替换它、清空房主刚选定的方案。
- 旧结果返回时若发现状态已经变化，系统会尝试接续最新快照的共同整理。

**专业表达**

细粒度乐观并发控制（Optimistic Concurrency Control）、异步结果过期检测、版本化决策状态。

**展示话术**

> 多人协商最大的技术难点之一，是人在持续修改，AI 却可能还在回答上一版问题。我们给需求、输入和上下文分别标记版本，让迟到的答案不能直接覆盖新的决定。

**代码依据：** [业务操作的版本检查][C11]、[异步回调与过期处理][C12]。已有用例专门检查迟到 Agent 不覆盖新分析与已选方案。[T01]

**表达边界：** 这是单实例应用内的版本与事务控制，不是分布式共识协议，也不是 CRDT 协同编辑。

## 三、第二梯队：把“可信协商”讲成具体机制

### 07. 私密表达与共享推演分层：减少不必要的信息暴露

成员在个人通道中表达原话、补充资料和拒绝原因。`public_context()` 去掉本人明细、条件请求、私密反馈等字段；`planning_context()` 将已确认的结构化条件去除原话、备注、待澄清项等字段，相同条件合并计数后供共同推演使用。

界面数据也按身份投影：他人的评分维度明细被移除，个人修改请求只返回给本人；私密补充默认仅本人可见，明确公开的资料才能进入公共补充上下文。

**专业表达：** 分层上下文工程、数据最小化、按身份投影、去标识的结构化条件聚合。

> **展示话术：** 系统需要理解群体约束，但公共讨论不必展示每个人的私密原话。我们把“用于计算的信息”和“向其他成员展示的信息”分层处理，让成员更容易先独立表达真实想法。

**代码依据：** [公共与规划上下文][C13]、[成员视图脱敏][C14]。

**必须说准：** 当前仍可能展示成员级预测分；少数组合条件也可能被推断出来源。这里不是完全匿名、差分隐私或端到端加密。已确认结构化条件会进入配置的第三方模型；代码不能证明从众偏差已经量化下降。

### 08. 输入来源回执：AI 的“参考了哪些资料”可以核对

`attach_intake()` 为本轮 Agent 记录输入版本、上下文版本、实际送入的公开补充 ID、公开提议与信息数量、成员确认数量，以及相关知识版本。模型给出的 `synthesis.source_ids` 会被过滤，只保留本轮真实可用的公开资料 ID。

因此，模型编造的来源 ID，或试图引用私密资料的 ID，不会直接变成公开整合的依据列表。

**专业表达：** 输入溯源（Input Provenance）、可核对的处理回执、证据引用约束。

> **展示话术：** 当 AI 说“我综合了大家的提议”，系统可以展示这轮实际提供了哪些公开资料、使用了哪一版输入，而不是只让用户相信一句总结。

**代码依据：** [输入回执与来源过滤][C15]。测试明确包含真实公开 ID、私密 ID 和虚构 ID，只允许真实公开 ID 留下。[T01]

**表达边界：** 回执证明资料被送入本轮上下文，不证明模型完整理解了每条资料，更不构成外部事实核验。当前公共补充上下文有数量截取，不是无限历史记忆。

### 09. Human-in-the-loop 授权：建议、草稿与正式事实分开

个人条件必须本人确认，修改请求绑定原偏好版本与输入版本，并有 `PENDING / ACCEPTED / REJECTED / STALE / EXPIRED` 等状态。程序限制可请求修改的字段，只有本人能回应。

候选事实也有类似边界：模型解析出的新增和修正候选先被设为未确认、未核验；房主采纳时检查草稿版本、候选 ID 和引用。只有明确提交核对结果，才可把相应事实转为确认状态。

**专业表达：** Human-in-the-loop、授权式状态变更、草稿与正式状态分离。

> **展示话术：** AI 可以提出建议，用户保留把建议变成事实的权利。个人条件由本人决定，候选资料由房主核对，程序负责检查这次授权是否仍对应当前版本。

**代码依据：** [条件修改与协商请求][C16]、[草稿采纳和个人授权操作][C17]。

**表达边界：** 当前自动协商请求主要针对本人的预算冲突，不能描述成通用自动谈判算法，也不能说 Agent 已能任意向其他成员发起条件变更。

### 10. 正式投票快照：让每一票都对应明确的方案与规则

发起投票时，后端重新校核选定方案，并复制方案快照，锁定选民名单、偏好版本、资源版本、输入版本、门槛及截止时间。投票必须携带当前 `session_id`，重复投票被拒绝。

投票期间，普通条件和候选修改被锁定。需要修改时先取消本轮，再进入协商；成员明确退出也会取消正在进行的投票，旧票不继承。未投票不计为接受，正式通过由真实票数决定。

**专业表达：** 快照式表决、版本绑定的共识记录、业务状态机。

> **展示话术：** 一张票的含义，不仅是“我同意”，还包括“我同意哪一版方案、面对哪些参与者、按照什么门槛”。WeDecide 把这些条件一起锁定，避免方案已经变了，旧票还在替新方案背书。

**代码依据：** [投票创建、取消、退出及授权处理][C17]、[投票结算][C18]。

**当前参数：** 默认门槛 `0.8`，8 人需 7 票；默认三轮，代码允许配置 1–5 轮。规则在正式投票开始后不能随意更改。[C09]

### 11. 三态校核与诊断分流：知道下一步该补什么、由谁处理

系统区分 `FEASIBLE`、`UNKNOWN`、`INFEASIBLE`；评分还返回有效维度覆盖率、成员评分覆盖率和 `partial` 标记。候选来源状态则单独表示未确认、用户提供或房主核验。

`decision_progress()` 根据真实状态输出收集需求、缺少候选、等待计算、缺少事实、存在冲突、比较、投票或结束等阶段，以及下一步和负责人。它还比较相邻分析版本，展示可行方案数量及具体候选费用、时间、群体分的变化。

**专业表达：** 不确定性显式建模、规则驱动的失败诊断、角色感知工作流、版本差异解释。

> **展示话术：** 数据不足和真实冲突需要不同的处理方法。WeDecide 会告诉大家：当前是需要房主补资料，还是需要寻找替代方案；并展示本轮修改究竟让哪些结果发生了变化。

**代码依据：** [校核及覆盖率计算][C07]、[进度诊断和版本差异][C19]、[前端角色相关下一步][C20]。

**表达边界：** “房主核验”是人提供的状态和依据链接，不代表系统自动核实了链接内容；诊断也不是对所有决策失败原因的通用根因分析模型。

### 12. 从接受到参加：人数变化后重新校核执行条件

`attendance` 与正式投票独立。结果页根据未明确拒绝参加的成员重新运行评价，检查固定费用分摊等变化；仍有成员待定时标记 `attendance_provisional`，提醒结果暂定。

**专业表达：** 执行前一致性检查、参与意愿与表决分离、动态成本重评。

> **展示话术：** 大家接受方案之后，实际参加的人数还可能变化。系统会基于新的参与情况重新检查费用与条件，同时保留已经形成的正式投票记录。

**代码依据：** [参与意愿更新][C11]、[结果页的重新评价][C14]。

**表达边界：** 当前覆盖人数变化后的规则重算，未接入真实预订、支付、库存或履约追踪。待定成员暂时计入，并明确标注暂定；不能称为已实现完整交易闭环。

## 四、第三梯队：让产品能够持续运转的工程亮点

### 13. 共享整理与个人访谈分开调度，兼顾协作连续性和资源边界

共同整理使用 `(room_id, '@shared-decision')` 队列键，个人请求使用 `(room_id, member_id)`，房主在共同整理进行时仍可回答自己的卡片。所有任务共用全局并发和待处理容量限制。

自动推进记录尝试过的输入版本、上下文版本和轮次，避免对未变化状态反复调用模型；当前分析有效时复用结果。默认配置为 AI 并发 4、待处理容量 32，容量可调整。版本中途变化时，旧任务完成后接续最新状态。

**专业表达：** 任务隔离、背压控制（Backpressure）、状态驱动编排、版本去重。

> **展示话术：** 大家可以同时表达，共同方案也能继续整理；系统用分开的任务通道和统一的资源上限，让个人输入与群体推演相互衔接。

**代码依据：** [自动推进与队列键][C12]、[任务协调器][C21]。测试覆盖房主访谈与共同整理并行、未变化输入不重复启动。[T03]

**表达边界：** 这是同一房间 Agent 的不同任务通道，不是多 Agent 群体涌现。没有跨进程持久任务队列，也没有 exactly-once 执行保证。

### 14. 模型协议适配与有限结构修复，降低供应商耦合

网关支持 OpenAI Chat Completions 兼容协议、Anthropic Messages 和自定义 JSON HTTP。结构化任务使用模型 Schema；兼容接口会自动尝试 JSON 模式，明确拒绝相关参数时回退一次，并按端点与模型缓存该能力限制十分钟，最多 64 项。

无效结构最多进行一次修复，使用本次剩余时间；Agent 修复计入总逻辑调用预算。响应大小、模型列表数量和超时均有界限。管理员可调整阶段提示词，程序仍追加固定输出规则，业务授权仍由后端执行。

**专业表达：** 模型网关、协议适配、能力缓存、Schema 校验、有限重试。

> **展示话术：** 模型可以更换，决策规则仍由系统掌握。接口适配层处理协议差异，结构校验层检查输出，业务层决定哪些内容有资格进入正式状态。

**代码依据：** [请求协议与兼容处理][C22]、[结构修复][C06]、[提示词分层组合][C23]。

**表达边界：** 协议支持不等于所有供应商都已验证；固定提示词不是提示注入免疫证明。

### 15. 轻量实时协作：推送变化信号，按身份重新读取最新状态

SQLite 以 WAL 模式持久化，房间写操作通过事务提交。SSE 只发送变更信号，客户端随后读取按身份过滤的状态；每个订阅队列容量为 1，短时间内的多个变更信号会合并，避免积累无意义的重复通知。

前端刷新时保留编辑内容、焦点和光标位置；输入草稿按房间和成员区分保存。长任务与界面更新因此能共存，减少填写中途被其他人的操作打断。

**专业表达：** 变更通知合并（Event Coalescing）、权威状态回读、轻量事务持久化、编辑态保全。

> **展示话术：** 实时协作需要同步最新进展，也需要保护用户正在输入的内容。WeDecide 把变化通知和状态读取分开，让每个人得到自己有权看到的最新版本。

**代码依据：** [SQLite 事务][C24]、[单槽实时通知队列][C25]、[编辑态保存与恢复][C26]。

**表达边界：** 当前为单进程设计，没有执行性能基准来证明高并发、超低延迟或 500 MB 内存目标。

### 16. 工具驱动的输入卡片与双场景引擎

当回答需要具体金额、时刻或文字时，模型通过结构化 `request_input` 声明字段与分支，后端映射成受限的数字、时间或文本控件。字段必须属于本题 `targets`，每个分支最多一个输入工具；打开控件只是本地交互，不增加追问张数，也不额外调用模型，真正提交时才发送数值。

场景层面，代码已有 `activity` 与 `decision` 两类资源。通用备选独立比较，活动资源进入行程搜索；单日活动搜索采用有界束搜索，每层最多检查 2,000 个安排、保留 48 条路径，并对手工行程使用同一评价器。

**专业表达：** 受控生成式交互（Constrained Generative UI）、领域分派、评价逻辑复用、有界束搜索（Bounded Beam Search）。

> **展示话术：** AI 可以根据问题请求一个合适的输入控件，应用负责控制字段类型和提交规则。同一套偏好与投票机制，也已经能承接通用方案比较和活动行程两类任务。

**代码依据：** [输入工具分派][C27]、[前端输入分支][C28]、[双场景评价与有界搜索][C29]。

**表达边界：** 这不是任意 UI 代码生成。通用备选仍依赖既有属性、费用和偏好模型；活动搜索不保证全局最优，不具备地图路线、自动商家检索或实时价格查询能力。

## 五、答辩最值得讲透的三个故事

### 故事一：问题、计算和解释形成了可核对的链路

从一张卡片开始：它指向真实算法字段，用户确认后形成正式条件；引擎据此进行校核，Agent 再读取计算结果解释取舍。这个故事可以同时展示自然语言理解、工具调用和业务约束之间的关系。

> **金句：** 我们让一个问题有计算目的，让一次解释有执行依据，让一个结论有对应版本。

### 故事二：公平性体现在整个流程中

成员先独立表达，必要条件不能被平均分抵消，群体评分兼顾最低预测满意度；需要妥协时由本人授权，投票时大家面对同一份快照。公平性在这里是一组共同工作的机制，而不仅是一个权重参数。

> **金句：** 公平既体现在怎样评分，也体现在谁能修改条件、谁能看见信息，以及谁有权作出最后决定。

### 故事三：系统认真处理“事情没有顺利发生”的情况

资料未知时保留未知，输出格式错误时有限修复，模型故障时保留计算，旧版本返回时阻止正式写入，没有共识时保存未通过的结果。失败有明确状态，用户知道已经完成什么、下一步该做什么。

> **金句：** 一个可靠的决策产品，需要在无法继续时说清原因，在还能继续时保住进度。

## 六、可直接使用的路演陈述

### 30 秒版本

WeDecide 是一个 AI 群体协商与决策平台。成员先独立表达需求，AI 用与真实算法关联的动态卡片澄清条件；确定性引擎检查每个人的底线，并比较群体整体与最低预测满意度。Agent 读取工具结果解释取舍，成员再针对同一版本正式投票。我们把语义理解、真实计算和用户授权接在一起，让多人决策有依据、可协商、能追溯。

### 约 2 分钟版本

我们经常遇到这样的场景：几个人一起做决定，讨论了很久，仍然不知道每个人真正关心什么，也不知道最后选出的方案究竟让谁作出了妥协。

WeDecide 从需求表达开始解决这个问题。每个成员通过私密卡片表达想法，AI 根据当前候选差异和算法缺口提问。每个问题都需要指向一个实际计算字段，整理出的条件也必须由本人确认。

接下来，确定性引擎检查方案是否满足每个人的必要条件，再比较平均预测满意度和最低预测满意度。Agent 可以调用真实校核工具，也可以在副本中做 What-if 推演，然后读取结果解释取舍。模型暂时失败时，已经完成的计算和有效草稿仍能保留下来。

多人操作过程中，系统用不同层次的版本号处理并发：旧条件、旧草稿和迟到的 AI 结果不能直接覆盖新状态。正式投票会锁定方案、成员和门槛；个人条件的修改需要本人授权，投票通过之后，参与人数变化还会触发费用与条件的重新检查。

我们的核心价值，是把这些机制连接成同一次决策：让每个人的需求能够被准确表达，让方案接受真实计算，让共识保留人的决定权。每一次提问都有目的，每一次推演都有依据，每一张票都有明确的版本。

## 七、现场演示：用一条主线证明核心亮点

建议以“两人选择共同活动或共同方案”为主线。提前准备少量明确标注为演示用的候选资料，不把虚构数据说成实时商家信息。普通演示使用已有界面；故障与并发属于技术加演，可用隔离环境和既有测试复现。

| 顺序 | 演示动作 | 要让观众看到什么 | 对应亮点 |
|---|---|---|---|
| 1 | 创建空间，两位成员分别表达需求 | 同一个目标下的独立输入 | 分层上下文 |
| 2 | 选择需要金额的卡片分支，填写具体上限 | 输入控件与问题目标关联，提交具体值后再进入下一步 | 契约访谈、受控交互 |
| 3 | 本人确认，房主核对候选事实 | 草稿成为正式数据需要明确授权 | Human-in-the-loop |
| 4 | 设置一个高于预算上限的候选 | 即使偏好得分较高，也无法绕过必要条件 | 硬约束优先 |
| 5 | 查看其他候选的费用、群体分和最低预测分 | 不同方案之间有具体取舍 | 多目标评价 |
| 6 | 在技术演示中调用 `simulate` 改变公平性权重 | 返回真实分数，同时正式规则不变 | 只读 What-if |
| 7 | 修改一个已经核对的费用 | 新分析展示可行数量及费用变化 | 全体重评、版本差异 |
| 8 | 选择可行方案，发起投票 | 两人默认门槛需要两票，第一票不能直接通过 | 快照表决 |
| 9 | 若需修改方案，先取消本轮，再发起新投票 | 旧票保留记录但不继承 | 版本化治理 |
| 10 | 结果后改变参与意愿 | 费用分摊重新计算，正式投票记录保留 | 执行前校核 |

**两个值得准备的技术加演：**

- **模型失败演示：** 在隔离测试中让工具成功、后续解释失败，展示计算结果仍保留，界面或返回值明确标记未完成说明。
- **迟到结果演示：** 暂停旧 Agent 请求，先生成并选定新方案，再释放旧请求，证明旧结果不会清空新选择。

这两项已有对应测试源码，适合工程答辩展示；不要把故障测试直接施加到真实用户房间。[T01]

## 十、答辩追问与建议回答

**问：你们的 Agent 到底有什么实际动作？**

答：它可以提出候选草稿，调用真实校核 `analyze` 和只读模拟 `simulate`，读取工具输出后形成下一步。正式条件、事实确认与投票仍由业务规则和用户授权控制。

**问：为什么不让大模型直接给方案打分？**

答：这里涉及预算上限、时间窗口和成员底线，需要稳定、可核对的规则。模型负责理解表达与说明取舍，确定性引擎负责已结构化条件的计算，两者通过真实工具结果衔接。

**问：你们的公平性创新在哪？**

答：评分公式本身并非声称首创。我们的工程价值在于把硬约束、最低预测满意度、独立表达、本人授权和快照投票放进同一条流程，让公平性要求从输入延续到决定。

**问：能保证找到最优方案吗？**

答：不能保证全局最优。活动规划使用有界搜索，通用备选在已有候选中比较；系统会记录范围和未知项，并展示已知维度上的取舍。

**问：模型胡说或接口出问题怎么办？**

答：结构化结果先经过字段与业务检查，必要时有限修复。失败时保留已有有效进度，并明确提示哪一步没有完成。事实仍须人核对，不能声称消除了所有幻觉。

**问：数据会不会泄露给模型？**

答：调用第三方模型意味着选定的上下文会发送给该供应商。系统做的是按任务最小化和区分公共、个人上下文，并不提供端到端加密推理或密码学匿名保证。

**问：多人同时操作为什么不会乱？**

答：房间状态通过事务写入，个人偏好、共同输入、上下文和投票分别校验版本；迟到的 Agent 结果会被识别，不能无条件覆盖新状态。当前保障范围是单实例实现。

**问：最能体现产品成熟度的细节是什么？**

答：全员确认后的计算不必等待模型解释；模型故障时保留实际结果；实时更新时保留正在编辑的内容；重复问题会结束而不是无限追问。这些细节让流程在不理想的情况下也能继续。
